2. Por que a arquitetura importa aqui

app-lello-essentials (115 deps diretas — TODAS as libs moram aqui)
        ↑ path:
app-lello-shared      (só depende de essentials)
        ↑ path:
 ┌─────┴──────┬─────────┬────────────┬─────────────┐
sindico      morar   colaborador   morar-viver   sindico-viver

Consequência prática

  • 90% do trabalho é em um único arquivo: essentials/pubspec.yaml.
  • O impacto de um bump errado é em 5 apps ao mesmo tempo. Não existe rollout gradual por app — se o essentials sobe, todos sobem.
  • morar-viver e sindico-viver são white-labels raramente testados, mas herdam tudo. Precisam entrar no smoke test.

3. Três blockers a resolver antes de qualquer bump

Blocker 1 · Divergência de Java entre os projetos
Bloqueante
ProjetoJavacompileSdk
sindico1.8 ⚠36 (hardcoded)
morar17flutter.compileSdkVersion
colaborador17flutter.compileSdkVersion

O sindico está em Java 1.8. Firebase 4.x e a maioria dos plugins Android modernos exigem Java 11+ (na prática 17). Sem subir o sindico para Java 17, o bloco Firebase não compila.

Ação: alinhar sourceCompatibility / jvmTarget para 17 e usar flutter.compileSdkVersion em vez do 36 fixo.

Blocker 2 · Overrides obsoletos no shared
Bloqueante 
# app-lello-shared/pubspec.yaml
dependency_overrides:
  analyzer: 6.4.1      # essentials já resolve 7.7.1
  source_gen: 1.5.0    # essentials já resolve 2.0.0
  dart_style: ^2.3.7

Esses pins estão travando o ecossistema de code generation (build_runner, drift_dev, chopper_generator, json_serializable). Enquanto existirem, não dá para subir os geradores. Provavelmente são resquício de um conflito antigo já resolvido.

Ação: remover os pins, rodar build e verificar se o conflito original ainda se manifesta.

Detalhamento das ondas de maior atenção

Onda 0 — Preparação (fazer primeiro, sem exceção)

  1. Subir sindico para Java 17 e alinhar compileSdk com os outros dois apps.
  2. Remover analyzer: 6.4.1 e source_gen: 1.5.0 do shared. Rodar build para ver se o conflito original ainda existe.
  3. Investigar quem trava share_plus e open_file (flutter pub deps).
  4. Criar baseline: build APK release dos 5 apps + flutter test + screenshots das telas críticas. É a régua de comparação de todas as ondas seguintes.
  5. Congelar pubspec.lock num commit dedicado antes de tudo.

Onda 1 — Ganho rápido

flutter pub upgrade (sem --major-versions). Pega os 65 patches e os 85 minors não-breaking. Zero mudança de código esperada. Valida rápido se o pipeline continua verde e já derruba boa parte da dívida.

Onda 5 — Firebase (a mais crítica)

  • Subir os 11 pacotes juntos, num único commit.
  • Reconferir google-services.json / GoogleService-Info.plist e as configs dos 10 flavors.
  • Testar em device físico: push notification chegando, crash forçado aparecendo no Crashlytics, remote config puxando valor novo.
  • Firebase é justamente o que falha silencioso: o app compila, roda, e só semanas depois se descobre que crash não está sendo reportado.

Onda 6 — Permissões

  • Testar cada permissão em Android 13, 14 e 15 (as regras mudaram em cada uma) e iOS 16+.
  • flutter_local_notifications 18→22: revisar canais de notificação e permissão POST_NOTIFICATIONS.
  • workmanager: revalidar o sync de ponto offline do colaborador (cenário GERAL-04 do roteiro de testes).

7. Riscos principais

1. Firebase 4.x pode exigir Flutter mais novo Se der conflito de SDK, entra na conta um upgrade de Flutter — que é outro projeto, com outro plano. Só descobrimos isso ao executar a Onda 5.
2. Oito pacotes têm latest > resolvable device_info_plus, file_picker, fluttertoast, package_info_plus, pdfrx, flutter_contacts, share_plus, open_file. Significa que o Flutter atual limita o teto. Vamos até o resolvable e o resto fica pendente de upgrade do Flutter.
3. Cinco apps de uma vez Qualquer bump no essentials afeta todos simultaneamente. Regressão em um app pode passar batido se o time só testar os outros. O smoke test precisa cobrir os 5.
4. White-labels esquecidos morar-viver e sindico-viver quase nunca são testados, mas herdam todas as libs. Incluir obrigatoriamente no critério de aceite.

8. Recomendação e próximos passos

Começar por Onda 0 + Onda 1 juntas Em aproximadamente 10 horas você tem: os blockers estruturais resolvidos, cerca de 150 pacotes atualizados, e um baseline confiável para comparar as ondas seguintes. Isso derruba boa parte da dívida sem risco de breaking change, e revela cedo se o Flutter atual vai virar gargalo.

Depois de fechar as duas primeiras ondas, avaliar com o time se vale seguir para as ondas 2 a 6 de forma contínua ou parcelar ao longo de sprints — considerando que as ondas 5 e 6 exigem janela de teste em devices físicos e múltiplas versões de Android/iOS.

Sequência sugerida de aprovação

  1. Aprovar este plano e a alocação de ~10h para Onda 0 + 1.
  2. Executar, validar e fazer merge.
  3. Reavaliar cronograma para as ondas 2-6 com dados reais de esforço das duas primeiras.
